## 压缩之后，谁的话还算原话

我最初把会话压缩理解成“写一份短一点的摘要”。实际做起来，麻烦出在另一个地方：摘要写完后，原来的话还在不在？

常见做法是全量摘要替换。系统截取一段历史，把用户消息、Agent 回复和工具结果一起交给模型。模型写完摘要，这段历史就被整块换掉了。

这种做法很利落。新上下文短，格式也统一。可它有个让我不太放心的地方：连用户原话也要经过一次转述。假设用户说的是“不要改存储层”，摘要却写成“尽量避免改动存储层”，一条硬约束就这样软了下来。下一轮 Agent 看不到原句，也无从发现这次偏差。

另一种做法，我在这里称为 Codex 型保留式清理。系统先生成一份压缩状态，再从最近的消息往前扫。遇到 Agent 回复或工具结果就删除，遇到用户消息则跳过，直到腾出足够空间。最后留下来的历史有两部分：模型写的压缩状态，以及用户当时输入的原文。

保留原话当然有好处，但也别高兴得太早。用户可能写过“就用你刚才的第二个方案”，而那个方案恰好在被删掉的 Agent 回复里。或者用户只说“修复这个错误”，错误堆栈却随着工具输出一起消失了。摘要得把这些断开的指代补回来，否则留下来的只是语法完整、含义悬空的句子。

我更愿意把两种做法看成不同的押注。全量替换把更多信任交给摘要模型；保留式清理则把用户原话当作不能随便改写的记录。选哪一个，要看系统更怕摘要失真，还是更怕上下文继续膨胀。

Codex 的[公开文档](https://learn.chatgpt.com/docs/developer-commands.md?surface=cli)只说明 `/compact` 会总结可见会话、释放上下文，没有解释上述逆序删除规则。文中的“Codex 型”指本文讨论的保留策略，不代表 Codex 已公开的内部实现。

## 压缩总要丢东西

如果什么都不丢，那只是搬家，不叫压缩。

工具刚刚打印的 1,800 行扫描结果，通常可以再跑一次。用户在半小时前说的“不要增加依赖”，就没那么容易补救了。失败方案为什么被放弃、某个猜测还没有验证，这些信息也常常只活在对话里。

所以“保留最近 N 条消息”并不可靠。消息的新旧和价值没有固定关系。一个很早的架构限制，可能比刚生成的十段日志更影响下一步。

当然，检查点也不能什么都收。写得太长，下一轮还得从头判断哪些结论已经过期。我希望压缩省下的，是重新弄清现场的时间。

## 别让压缩替记忆和检索干活

压缩服务于眼前这段会话，让任务跨过上下文边界。长期偏好和项目约定更适合放进记忆。代码、日志和旧记录如果随时能查，就留给检索。

这个区分能省掉不少无用文字。代码里已经写清楚的事实，检查点记一个文件位置就够了；只在会话里出现过的决定，则要多写一句原因。复制整段代码通常是在浪费预算，漏掉一句“为什么不这么做”却可能让后面的工作绕回原点。

## 一份很顺的摘要，反而容易骗过人

压缩出错时，系统通常不会报警。它会交出一段语法通顺、结构完整的文字。下一轮读起来毫无阻力，也就很容易把尚未验证的猜测当成事实，或者重新捡起早已排除的方案。

我希望检查点把状态写明白：哪些是已经确认的事实，哪些只是当前决定，哪些仍在猜，接下来准备做什么。这里不用追求文采。“还不知道”比一段为了顺畅而补出来的解释靠谱。

## 我更关心恢复要花多少力气

压缩率很好算，恢复成本却更接近真实体验。找一个没读过原会话的 Agent，只给它检查点和当前工作区，看看它从哪里开始。

它如果先重复调查半天，说明检查点漏了现场。重新提出被否定的方案，多半是因为理由没留下。能从正确的位置继续，这次压缩才算管用。

## 这已经是运行时行为

短对话里，压缩只是偶尔出现的整理动作。任务一长，Agent 开始改代码、跑工具、等待外部反馈，压缩就会反复发生。每压一次，系统都要重写一遍自己所相信的过去。

这也是我觉得它值得单独设计的原因。少保存几条消息没什么，悄悄改掉一句用户约束，后面的每一步都会跟着偏。
