我最初想把 Agent 的发展写成一条很顺的线：

```text
Prompt Engineering
        ↓
Context Engineering
        ↓
Harness Engineering
        ↓
Loop
```

这几个词确实能连起来，只是不能把它们当成前后替换的四代技术。早在 2022 年，[ReAct](https://arxiv.org/abs/2210.03629) 就已经让模型在推理、行动和观察之间循环。现在讨论的 loop 是外面那一层：不再等人类给出下一条指令，而是由系统继续创建任务、启动 Agent、检查结果，再决定下一轮做什么。

我更愿意把这条线看成工程边界逐渐向外移动。最早我们调一句话，后来开始安排模型在每一轮能看到什么，再后来要为它搭一个能工作的环境。到了 loop，连“接下来该不该继续工作”也交给了系统。

## Prompt 先解决一次回答

Prompt engineering 最容易观察。换一句指令，加两个示例，调整输出格式，结果马上不同。在主要用例还是分类、摘要和单轮生成时，一次模型调用几乎就是整个产品，prompt 自然成了最显眼的工程对象。

它的问题也很直接：prompt 只能影响这一次推理。任务一长，模型还要查资料、修改文件、等待命令和处理失败，光靠开头那段话很难守住现场。

Prompt 并没有过时。后面的每一层仍然需要清楚的指令，只是很多看起来像“不会听话”的问题，已经不能靠换一种措辞解决了。

## Context 决定模型这一刻知道什么

工具调用和检索把问题推到了 prompt 外面。系统提示、用户消息、工具定义、搜索结果、文件内容、历史对话和阶段性计划，最后都会变成同一个上下文窗口里的 token。

窗口再大也不能什么都塞。[Anthropic 对 context engineering 的定义](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)不是“写更长的 prompt”，而是在每一次推理前，挑选并维护当下最有用的信息。Agent 跑得越久，这件事越难。刚刚打印的两千行日志也许可以删掉，半小时前用户说的边界条件却未必能补回来。

这时工程师开始处理一种动态状态：什么应该常驻，什么按需检索，什么需要压缩，什么必须原样保留。Context engineering 管的不是一句话，而是模型此刻所处的认知现场。

但知道得足够多，仍然不等于能把工作做完。

## Harness 给 Agent 一个可以工作的地方

Agent 要修改真实世界，就需要工具接口、文件系统、权限、沙箱和退出条件。它还需要在失败时看到测试结果，在上下文耗尽后留下进度，让下一次会话知道哪些路已经试过。

这些东西合在一起，常被叫作 harness。边界没有公认的精确画法，大致可以理解成模型之外、负责让模型稳定工作的那套系统。上下文管理和 agent loop 通常也在里面。

2024 年的 [SWE-agent](https://arxiv.org/abs/2405.15793) 已经说明，专门为模型设计的计算机接口会直接改变 Agent 的表现。后来 Anthropic 在[长任务 harness 实验](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)里加入初始化会话、进度文件和 Git 历史，让多个上下文窗口之间可以交接工作。

这里的变化很实际。Agent 做不好时，问题不一定是模型不够聪明，也可能是测试输出太吵、文档找不到、工具返回的信息不适合机器阅读，或者“完成”根本没有可检查的定义。继续修 prompt 往往只是碰运气。Harness engineering 会追问：环境里到底缺了什么证据，或者哪条约束还只存在于人的脑子里？

## Loop 让 harness 自己转起来

一个能用的 harness 仍然可能需要人守在旁边。Agent 停下，人检查一下，再告诉它继续。最近的变化是把这次接力也自动化。

最简单的是 Ralph loop。Agent 声称完成后，外层脚本再次把它送回任务，要求它对照成功条件检查。Anthropic 在[长时间科学计算的实践](https://www.anthropic.com/research/long-running-Claude)中用这种方式让 Claude 持续逼近一个数值精度目标。真正起作用的不是“再问一遍”，而是旁边有参考实现、测试和明确的误差阈值。没有这些东西，循环只会让一个含糊的任务运行得更久。

Anthropic 的 [C 编译器实验](https://www.anthropic.com/engineering/building-c-compiler)又向前走了一步。16 个 Claude 实例在共享代码库上工作，前后经历约两千次 Claude Code 会话。每个会话领取任务、修改代码、运行测试并提交；会话结束后，系统在新容器里启动下一个 Agent。Git 保存长期状态，任务锁避免重复劳动，编译器测试套件负责告诉它们有没有真的向前走。

这已经不是一个 Agent 活得更久，而是一套系统不断生成新的 Agent 工作轮次：

```text
目标、测试与共享状态
          ↓
      启动新会话
          ↓
   选择任务并执行
          ↓
     验证与提交
          ↓
    更新进度和失败记录
          └────────→ 下一轮
```

另一种做法是把判断工作交给独立角色。Anthropic 后来的[长应用开发实验](https://www.anthropic.com/engineering/harness-design-long-running-apps)使用 planner、generator 和 evaluator：先把短需求展开成规格，再实现，最后由另一个 Agent 操作真实页面并挑错。评价不过关，反馈就回到 generator。把生产者和评价者分开，比让同一个 Agent 一边交作业一边夸自己可靠得多。

我觉得这才是“loop”值得单独列出来的原因。Harness 原本描述环境里有什么；loop 描述这些部件怎样在时间里反复运转。调度、交接、验证和重启被接起来以后，人不必再批准每一个下一步。

## 循环会把错误也自动化

Loop 听起来像更高一级的自动化，但它不会自动带来正确答案。C 编译器实验最费心的部分不是那个 `while true`，而是测试、反馈和任务划分。等所有 Agent 都堵在同一个 Linux 内核编译错误上，并行数量再多也没有用。后来加入 GCC 作为 oracle，问题才重新变得可以拆分。

评价器也不是天然公正。Anthropic 在 generator–evaluator 实验中发现，Claude 做 QA 时会发现问题，然后说服自己“这不算大事”。评价 prompt 需要根据真实误判反复校准。循环依赖什么信号，就会很勤奋地优化什么信号，包括写错的信号。

成本同样没有消失。C 编译器实验花了接近两万美元；一个完整应用的多 Agent harness 跑六小时约两百美元。自治时间变长以后，停止条件、预算和权限边界不再是外围配置，它们决定一次错误能跑多远。

还有一件容易忽略的事：harness 不会只增不减。模型升级后，过去用来弥补能力缺口的脚手架可能变成负担。Anthropic 换用更强模型后，就移除了部分上下文重置和 sprint 拆分。好的 harness 不是组件最多的那个，而是刚好保留当前模型仍然需要的约束。

## 人从回合里退出来

回头看这条线，变化的不是 prompt 被谁淘汰了，而是人站的位置。

写 prompt 时，人直接规定模型怎样回答。做 context engineering 时，人安排模型在每一轮看到什么。搭 harness 时，人准备工具、现场和证据。进入自治 loop 后，人更多是在循环外定义目标、验证器、资源边界和中断点。

这也解释了为什么最后一步比前几步更让人兴奋，也更让人不安。凌晨三点，Agent 团队仍在领取任务、修改代码和互相接班。只要测试持续变绿，它们就会继续。此时最重要的问题已经不是“prompt 写得好不好”，而是我们有没有把真正想要的结果写进这个世界。
