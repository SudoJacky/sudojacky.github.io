以前我以为，Coding Agent 的主要消耗发生在它写代码的时候。后来盯过几次完整会话，才发现真正容易浪费的地方往往更早：它为了找到两份相关文件，先读了十几份不相关的文件；测试命令打印了几百行成功记录；任务早已换了，会话里还拖着上一个问题的日志。

最后可能只改了四行代码，模型却在后面的每一轮里反复带着这些旧内容。

我现在会把一次 Coding 会话当成一个不断变重的工作台。放上去的东西不只用一次。文件内容、命令输出、工具返回和前面的讨论，通常都会跟着下一次请求再次进入上下文。缓存能让重复读取便宜一些，却不会让无关内容消失，模型仍得在里面找出眼前真正有用的部分。

我真正想省的是被花在错误地方的 token。

## 一次请求带着整段会话回来

Coding Agent 的界面很像聊天框，容易让人误以为每次只发送刚输入的那句话。实际工作时，一次请求通常还包含系统指令、工具定义、项目约束、先前读过的文件，以及刚才命令打印的结果。

假设我让它「修复 `price.test.ts` 里的失败用例」。它先读取测试文件，下一轮带着测试文件去读实现，再带着两份文件做修改，随后运行测试。每次工具调用都会给会话追加新内容，下一轮再把已有内容带上。

这也解释了一个以前让我困惑的现象：前十分钟很利落，聊久了以后，同样简单的修改却开始迟钝。问题未必是窗口快满了，也可能是相关信息在一堆已经没用的搜索结果和旧输出里变得难找。

我用一个很粗的式子提醒自己：

```text
会话负担 ≈ 进入上下文的内容 × 它留在后续会话里的轮数
```

越早进入的无关内容，陪跑越久。第一轮读错的一份大文件，通常比收尾前多说两句话更浪费。

![五轮请求逐步累积文件、命令输出与历史内容，越早加入的信息在后续轮次重复出现越多](/images/notes/efficient-coding-agent-sessions/context-snowball.webp)

## 先把模型和思考强度定下来

模型大小和思考强度应该跟任务难度匹配。查一个明确的类型错误、改一处文案，不需要先用最重的配置；架构取舍、并发问题和原因不明的故障，才值得给更多推理预算。

我会在会话开始前做这个选择，尽量不在中途反复切换。支持 prompt cache 的工具通常按请求前缀复用计算结果。模型、思考强度或前部系统配置一变，原来的前缀就可能对不上，后面那一大段历史需要重新处理。

中途发现任务比预想中难，当然应该换。只是换完以后，我更倾向于开一个干净会话，把已确认的事实、相关文件和剩余问题交过去，而不是让新配置接手一条已经很长的旧对话。

## 告诉它从哪里开始

「测试坏了，帮我看看」把定位工作也交给了 Agent。它得先找测试命令，再搜索失败用例，读几个名字相近的文件，最后才碰到真正的问题。这些探索有时必要，但如果我已经知道入口，就没理由让它重新猜一次。

我现在会尽量给出四样东西：失败的测试、目标文件、我观察到的现象，以及不能越过的边界。例如：

> 修复 `src/cart/price.test.ts` 中折扣叠加的失败用例。实现位于 `src/cart/price.ts`，不要改金额的舍入规则。先复现，再做最小修改并单独运行这个测试文件。

如果客户端支持把文件直接附到消息里，我会在第一条消息附一次。重复附同一份文件只会在上下文里多出副本。路径不确定时，也可以先自己找准入口，再开始正式会话。几十秒的人工定位，经常能省掉好几轮漫无目的的搜索。

不过，明确入口不等于替 Agent 下结论。「问题在第 42 行，把这个判断删掉」可能把错误假设写进任务。我更愿意给它证据和边界，根因仍让它验证。

## 命令输出也会留在现场

文件很容易引起警惕，终端输出却常被忽略。测试、构建、`git log` 和静态检查打印出来的内容，同样会进入会话。

最麻烦的不是一眼就装不下的超大日志。很多客户端会把超长输出截断或另存为文件。更常见的是几百行「全部通过」：体积没有大到触发截断，又足够在后面每一轮里制造噪声。

我会给常用命令准备安静的版本：只跑相关测试文件，使用简洁 reporter，只显示错误，查询日志时限制数量。项目约束文件里也会直接写清这些命令，免得 Agent 每次重新试参数。

如果命令确实会产生大量输出，我会让独立工作会话处理。它可以在自己的上下文里读完整日志、反复搜索，主会话只接收带位置和证据的结论。

## 新任务开新会话，同一任务才压缩

我以前喜欢把一天的工作都放在一个会话里，觉得这样 Agent「记得更多」。实际效果通常相反。修完登录问题后又去改搜索页，前一个任务的组件、日志和讨论不会自动退场，只是变成后一个任务的背景噪声。

现在我的分界很简单：目标变了，就开新会话；目标没变，只是前一阶段已经结束，才考虑压缩。

新会话适合切断无关历史。压缩适合保留同一任务的现场，例如已经确认的根因、改过的文件、失败过的方案和剩余验证。压缩之前我会明确要求保留什么，因为一份写得很顺的摘要，最容易把「尚未验证」悄悄写成「已经确认」。

准备离开很久时，我也会先留下一个短检查点。等缓存过期后再恢复一条长会话，往往不如从这份检查点和当前工作区继续。需要保留原会话时，先给它改一个能搜到的名字，之后再开新任务。

定时检查和循环任务也应该有自己的短会话。每次轮询都是完整的一轮，没必要让它背着我下午修 bug 时留下的全部上下文。

## 独立工作会话不是越多越省

隔离上下文很有用，但拆出去的工作也有启动成本。新的工作会话没有主会话的历史，常常要重新读取项目约束和相关文件。一个两分钟能完成的小改动，硬拆出去只会重复准备工作。

我通常只隔离两类任务：输出很多但最终只需要少量结论的工作，以及可以独立调查、不需要持续共享判断过程的工作。比如分析构建日志、扫一批文件找相同模式、核对几份外部资料。

交出去的任务要写清返回格式。「看看这份日志」不够，我会要求它只报告失败项、对应位置、最可能的原因和原始证据。主会话拿到的是可以继续行动的结果，而不是另一份更短、但仍然含糊的摘要。

重复发生的高噪声任务，可以固定用较小的模型和专门指令。一次性的简单动作留在主会话里更划算。

## 我现在怎样开始一段 Coding 会话

动手前，我会花半分钟过一遍下面几件事：

1. 这是不是一个新目标？如果是，别复用旧会话；
2. 我能不能直接指出测试、文件和约束，少让 Agent 搜几轮；
3. 任务需要多大的模型和思考强度，能否一开始就定好；
4. 接下来哪些命令会很吵，是否有单测、安静参数或独立会话可用；
5. 如果中途离开，要留下哪些已确认事实和下一步。

这些习惯不会让每次会话都变短。难题仍然需要读很多代码、跑很多轮验证。有区别的是，那些内容确实服务于眼前的问题。

我判断一次会话是否高效，也不再只看用了多少 token。更有用的问题是：上下文里的每一块东西，后面还会不会用到；每一次工具调用，是在推进修改，还是在弥补一开始没说清楚的入口。

代码最后只改四行并不代表任务简单。至少别让另外十份无关文件陪着这四行一起跑完全程。
