Raft 的文章从一个很小的实验开始：让房间里的 Agent 轮流报数，每个 Agent 只说一个数字，不能重复。结果通常排不成整齐的一列。几个 Agent 同时发出「1」，接着又有几个一起说「2」。

第一反应很容易落到模型身上。是不是 Agent 不会观察？不会礼让？指令理解得不够好？

但这篇[《Is Having Agents in the Room Meant to Be Chaotic?》](https://raft.build/resources/blog/is-having-agents-in-the-room-meant-to-be-chaotic/)给了一个更有用的解释：Agent 没坏，房间的交互模型不适合它。

![多个 Agent 在共享房间里同时发出回复，信号在中央发生碰撞](/images/notes/agent-room-coordination/simultaneous-replies.webp)

## Agent 并不住在房间里

人待在群聊里时，感知几乎是连续的。我们能看见别人正在输入，能察觉话题已经转向，也会在开口前停半秒，确认刚才那句话没有被别人说掉。这些细节平常不值得专门设计，因为人本来就在场。

Agent 的时间却是一段一段的。一次调用里，它读取房间的快照，开始推理，生成动作，然后把动作提交出去。两次调用之间，它什么也看不见。

```text
读取 room@17  →  推理  →  提交一条基于 room@17 的回复
                    ↘ 此时房间可能已经来到 room@23
```

问题出在最后一步。Agent 做判断时看到的状态，和消息真正进入房间时的状态，可能已经不是同一个世界。别人已经回答了，任务已经被领走了，甚至讨论的问题都变了。它仍然把那条逻辑自洽、时机错误的回复发了出来。

这很像数据库里的并发写入，不太像传统聊天机器人的回答质量问题。

![Agent 仍在读取旧快照时，共享房间已经连续进入多个新状态](/images/notes/agent-room-coordination/stale-room-snapshot.webp)

## 用 @mention 换安静，代价是退回工具模式

最常见的补丁是只允许被点名的 Agent 回复。房间确实安静了，可 Agent 也失去了旁听和主动判断的空间。它看不见发错频道的任务，不能在错误假设刚出现时提醒，也无法决定「这件事虽然没叫我，但我应该说一句」。

另一种做法是把每个 Agent 关进独立会话。这能避开抢话，却把多人协作重新拆成了人工转发。人负责搬运上下文，Agent 仍然只是等待调用的工具。

Raft 把需要补上的设计称为 Agent Experience，简称 AX。这个名字带着产品定义新类别的味道，不过它问的问题很实在：Agent 行动时到底看见什么？两次调用之间留下什么状态？失败后能从哪里接着做？哪些判断可以由它自己作出？

## 收件箱不该直接塞进 Prompt

群聊通常把频道里的新消息推给 Agent。Agent 只有两个选择：全部处理，让闲聊和无关更新占满上下文；或者提前过滤，承担漏掉重要消息的风险。

Raft 的 agent inbox 把消息改成可查询的待处理项。提及、线程更新和通知先留在收件箱里，Agent 有空时主动拉取，再决定哪些内容值得进入工作上下文。没有拉取的消息仍可查询，但不会自动挤掉任务状态、约束和中间结果。

这里改变的是注意力的所有权。上下文窗口保存 Agent 当前工作所需的内存，不必复制整段频道记录。每放进一条新消息，就会排挤别的东西。让房间按发送顺序决定 Agent 看什么，等于把最稀缺的资源交给最吵的参与者。

当然，拉取模型也会制造新问题。低优先级事项可能永远留在队尾，Agent 也可能因为错误判断漏看重要信号。一个能投入使用的 inbox 还需要优先级、老化、截止时间和重新提醒，不能只提供一个查询接口。

## Held draft 是一次提交前的版本检查

原文里最有意思的设计是 held draft。Agent 写回复时会带上自己读取的房间版本。服务端准备发送时，把这个版本和房间当前状态比较：

- 房间没变，正常提交；
- 房间已经前进，先扣住草稿，并告诉 Agent 在它写作期间发生了什么。

草稿会被保存成一份可以继续处理的状态，发送冲突不再直接变成失败。Agent 可以根据新消息重写，保留原文再试一次，什么也不发，或者在反复发生冲突后明确选择强制提交。

如果换成分布式系统的语言，这就是乐观并发控制：读取版本，基于旧版本准备写入，提交前做一次 compare-and-swap。系统把冲突变成新的决策点，让写入者决定下一步。

![Held draft 在消息进入共享房间前执行版本检查，并保留多个后续动作](/images/notes/agent-room-coordination/held-draft-checkpoint.webp)

这里有两个细节比动画般流畅的聊天体验更重要。第一，沉默是合法结果。Agent 发现别人已经说清楚后，可以丢掉草稿，不必为了证明自己工作过而留下一条消息。第二，强制发送必须是知情后的动作。系统可以提示状态过期，但不应在 Agent 已经看到变化后替它做内容判断。

## 把内部判断变成系统里的显式动作

人看到别人抢先回答，脑子里会自然完成「算了，不发了」。软件只需要一个发送框，不必把这条心理分支画出来。

Agent 不一样。它需要系统明确提供「重写」「沿用」「放弃」「知情后继续」这些动作，以及每种动作会保留或丢掉什么状态。原文把这叫 action explicitness。我更愿意把它理解为：不要指望模型从一个模糊的失败里猜出状态机。

同样，perception empathy 也不只是多给上下文。设计者要站在一次调用的边界上检查：Agent 看不到哪些人类不费力就能感知的信息？房间版本、任务是否已被领取、谁正在处理、草稿期间新增了什么，这些都应该成为结构化状态，而不是埋在几百条聊天记录里等模型自己找。

## 过期回复只是协作冲突的一种

Held draft 能拦住一条不合时宜的消息，却拦不住已经发生的副作用。两个 Agent 同时领取工单、同时修改文件、同时调用付费 API，不能靠发送前再看一眼群聊解决。

对会产生副作用的 Agent，房间还需要另一套约束：任务领取要有租约或原子 claim，外部调用要有幂等键，文件修改要经过合并和验证，长任务要暴露可查询的所有权。聊天层的版本检查和执行层的并发控制是两件事。

Raft 也承认，inbox 和 held draft 没有解决所有权、实时感知与完整协调。原文提到他们的报数实验可以顺利超过二十，但这更适合作为产品设计的示例，不是多 Agent 协调已经解决的证据。

## 如果把这套思路放进自己的 Agent 系统

我会先检查下面这些边界：

1. 每次推理是否记录了输入快照的版本，还是只保存一段无法比较的新旧文本；
2. 新消息能否先进入可查询队列，由 Agent 选择接收、延后或忽略；
3. 回复和工具调用之间，哪些动作需要提交前的新鲜度检查；
4. 草稿、失败和沉默是不是可恢复的状态，而不是一律压成成功或异常；
5. 任务所有权是否独立于聊天消息，有没有 claim、租约、幂等和冲突处理；
6. Agent 作出「不行动」的决定时，系统能否留下足够的原因供人复核。

这篇文章把群聊里的混乱从「Agent 太爱说话」改写成了一个系统设计问题。Agent 无法连续感知，那就给它版本；上下文装不下整个房间，那就给它收件箱；行动可能过期，那就把草稿留在提交边界上。

AX 这个名字没那么重要。更实用的判断方法是：先看 Agent 在行动那一刻实际拥有的状态，再讨论它为什么做错。
