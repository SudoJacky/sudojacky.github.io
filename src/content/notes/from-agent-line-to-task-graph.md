前两天读到一篇关于 [Graph Engineering](https://x.com/0xCodez/status/2079165300625330317) 的帖子。作者把多 Agent 工作流拆成节点和边，我顺手拿自己常写的流程对照了一遍，发现不少等待是写任务时随手加进去的，数据上并没有依赖。

很多多步骤 Agent 看起来很复杂，实际仍是一条队伍：

```text
读取代码 → 检查安全 → 检查性能 → 运行测试 → 写报告
```

这里面只有一部分顺序是真的。安全检查和性能检查读取同一份代码，却互不依赖；运行测试也未必需要等两份审查都结束。它们之所以排成一条线，多半只是因为人习惯逐句下指令。

这篇笔记想弄清一件事：哪些步骤确实该排队，哪些可以拆开。

## 线性流程本来就是一张图

一条 `A → B → C → D` 的流水线当然也算图，只是很窄。每个节点只有一个入口和一个出口。C 慢了，D 只能等；C 失败，D 也没有机会启动。

我现在设计这类流程，通常先检查箭头，再考虑要不要增加 Agent。

判断一条边是否存在，可以问一个很朴素的问题：

> 下一步会不会读取上一步产生的数据？

如果下一步用不到上一步的结果，它们之间就没有依赖。需求里的“然后”经常只是语气词，系统没必要照单全收。

```text
                 ┌→ 安全审查 ─┐
读取变更与约束 ──┼→ 性能审查 ─┼→ 去重与验证 → 汇总结论
                 └→ 测试影响 ─┘
```

很多流程拆到这里就够了，一条长队变成三个并行检查，再汇总一次。

## 节点离开共享对话也要能工作

两个步骤要同时启动，每个步骤就得离开共享对话也能理解自己的任务。

节点要有明确输入，只做一件事，并约定输出格式。缺了其中任何一项，下游都得靠猜。

“帮我看看这里有没有问题”很难单独运行。它依赖共享对话里的暗示，输出也只能等人读完再解释。

可以把任务写得具体一些：读取指定 diff 和编码规范，只报告能够定位到文件与行号的正确性问题，返回 `severity`、`location`、`evidence` 和 `explanation`。这样的节点容易重试，也方便后面复核。

Schema 的用途也在这里。JSON 漂不漂亮无所谓，下游能按约定读取才重要。

## 边上多半是普通代码

节点约定好输入和输出后，边就很简单了：A 产生一份数据，B 正好读取它。

中间有不少工作用普通代码就能完成：

- 展平数组；
- 删除空结果；
- 按路径去重；
- 按阈值决定是否进入下一阶段。

我以前也会让模型顺手去重，后来发现这既费 token，又很难保证每次规则一致。能用几行代码说清的转换，就留在边上做。模型更适合处理语义含糊、需要权衡的部分。

一张 Agent 图里不需要到处都是 Agent。确定性的工作越少经过模型，运行结果越容易解释。

## 开得出去，也要收得回来

看到十个来源时，很容易立刻启动十个研究节点。二十个文件，似乎也该配二十个审查节点。

跑完以后拿到的只是一堆局部结果，还得有人收拾：

```text
fan out → reduce → synthesize
```

先并行收集，再用代码去重和过滤，最后交给一个需要看全局的节点综合。这个顺序很实用。

汇合点会等上游全部结束，它也是一道屏障。跨来源去重、统一排序，或者判断结果是否为空，都需要等完整集合。除此之外，我会尽量少加屏障。

如果每一项都能独立进入后续阶段，就让它们各自向前流动。没必要等最慢的一项到达后再集体出发。这样的等待在图上只是一条线，运行时却可能是几分钟。

## 路由交给代码，判断留给模型

任务不必每次都走同一条路径。

小改动做一次快速审查就够了。改动范围大时，再分别检查正确性、安全和性能。高风险操作还要停下来等人确认。

风险分类需要理解上下文，可以交给模型。分类完成后，走哪条路，由明确的 `if` 或 `switch` 决定。

```text
模型判断风险等级
        ↓
代码读取结构化结果
   ┌────┴────┐
 LOW        HIGH
   ↓          ↓
快速检查    多视角审查
```

以后想知道某次审查为什么被跳过，看分类结果和路由规则就行，不必回放一段模型对话。

## 我更愿意把预算留给验证

多一个 Agent 未必增加可信度。五个节点使用相同输入、提示和模型，很可能把同一种误判复制五遍。

如果预算还有余量，我会先加验证节点。它不负责补充内容，只尝试推翻上游结论：

- 这个问题能否复现；
- 证据是否真的支持结论；
- 是否忽略了已有保护；
- 严重性有没有被夸大。

验证者也会错。让它们使用同一种视角，只会制造虚假的多数。我更关心职责是否有差异：有人复现，有人找反例，也有人核对安全边界。

汇总时只保留经得起复核的发现。其余内容留在执行记录里，不必挤进最终报告。

## 循环要有结束的证据

有些任务没法预先估算规模。排查一个问题会暴露另一个问题，扫描一轮后还要沿着新线索继续找。这时图里需要一条返回前面的边。

最麻烦的循环并不会报错。它很勤奋，只是每一轮都在重复上次的死路。

我会给循环设置这些约束：

- 明确的停止条件；
- 总轮数、时间或费用上限；
- 对所有已见结果去重；
- 每轮新增结果和退出原因的记录。

去重范围很容易写错。被拒绝的候选也属于“见过”，否则下一轮会再次发现同一条死路，验证一遍，再拒绝一遍。

“连续两轮没有新发现就停止”比“继续，直到完成”可靠。凌晨三点没人盯着时，我希望系统执行前一种规则。

## 局部失败可以继续，但要留痕

某个来源暂时不可用时，其他节点可以继续，汇合点也可以接受缺失输入。最终结果要说明缺了什么、哪一步失败，以及报告因此少覆盖了什么。把异常悄悄变成 `null`，交出来的仍是一份残缺报告。

并行写入还有另一种麻烦：节点会争抢文件、分支或共享状态。有写冲突时，需要独立工作区和明确的文件所有权；只读节点则不用支付这笔隔离成本。

一次执行结束后，我至少要能查到：

- 启动过哪些节点，各自收到什么输入；
- 哪个节点失败或超时，命中了哪条路由；
- 哪些发现被验证节点淘汰；
- 循环为什么继续，最后又为什么停止。

这些记录平时很无聊。等一个并行流程偶发漏掉结果时，没有它们更无聊。

## 我会先从一张小图开始

图工程很容易被讲成规模竞赛，仿佛节点和 Agent 越多越好。

实际设计时，我按下面的顺序来：

1. 先写出最终需要的结果；
2. 找出产生这些结果的独立工作单元；
3. 只保留真实的数据依赖；
4. 把确定性的转换留给代码；
5. 给重要结论加验证，再决定哪些节点并行。

三个节点够用，就不启动三十个。我想知道每一次等待在等什么，每一次模型调用又解决了什么问题。

Prompt、harness 和 loop 关心一次推理怎样发生，Agent 怎样接触真实环境，以及系统怎样继续下一轮。任务图关心工作之间的关系。当任务放不进一段上下文时，可以把判断拆开，但证据还得在合适的位置重新汇合。

小任务用线性流程最省事。任务变大以后，再根据真实依赖把它拆开。别因为一句话里先写了 A、后写了 B，就让 B 无端多等几分钟。
